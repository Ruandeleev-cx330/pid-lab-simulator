# 随机挑战与可解性验证

## 目标

每轮给出**可解、但尚未达标、且物理上可存活**的初始 PID 参数，而不是无意义的随机数字。
同时保证：同一项目正常情况下物理参数恒定，用户调参才是唯一变量。

## 随机源

`src/challenges/rng.ts`：mulberry32 种子 PRNG。

- `generateChallenge(project, difficulty, seed)` 对同一 `(项目, 难度, 种子)` 完全可复现；
- 重试使用 `deriveSeed(seed, attempt)`，因此“第 N 次尝试”也是确定性的；
- 挑战 ID = `项目-难度-种子36进制-尝试序号`；`createdAt` 特意不写入挑战对象（否则不可复现）。

## 抽样

每个项目 / 难度各自定义（`src/projects/*/index.ts` 的 `DifficultyPlan`）：

```ts
targetRange   // 目标值区间（按输出精度取整）
initialRange  // 初始状态标量（温度初值 / 初速 / 初始液位 / 初始倾角）
gainSample    // Kp/Ki/Kd 的抽样带（位于滑块量程之内）
disturbance   // 场景扰动（可 required / 可 autoAt 自动注入 / 可完全可选）
criteria      // 该难度的全部达标阈值
timeLimit     // 挑战时限
```

抽样带是**离线校准**出来的“典型可用但未调好”的区域，而不是整个量程：

- 稳定对象（温度 / 电机 / 液位）的抽样带偏向低增益/低积分，响应偏慢、稳态误差偏大；
- 不稳定对象（平衡车 / 倒立摆）的抽样带偏向**欠阻尼**（Kd 偏低），表现为明显摆动，
  但 Kp 仍高于重力阈值，保证 8–9 s 内不会倒——用户能看到“在摆，但还没摔”。

## 生成流水线

```
for attempt in 0..19:
    rng = deriveSeed(seed, attempt)
    (target, initial, gains) = sample(rng)
    challenge = {...}

    ① 退化检查      |target − y0| ≥ minStep              （避免“目标=初值”的空挑战）
    ② 可解性验证    用内部参考策略真跑一遍 → 必须 success
    ③ 存活检查      初始增益跑 minSurvivalTime 秒 → 不得触犯安全包络
    ④ 可玩性检查    初始增益跑满时限 → 不得触发单调门槛、不得失稳
    ⑤ 通过 → 返回；否则记录诊断并继续
    兜底：若 20 次内没有任何候选通过 ⑤，返回一个“初始参数已可达标”的候选
抛出 ChallengeGenerationError(诊断列表)          // 有界重试，绝不无限循环
```

- ② 是真正的“存在解”证明：参考策略从**本轮抽到的初值与目标**出发，在**本轮时限**内达标；
- ③ 只检查安全包络（倒下 / 越界 / 数值故障），不检查指标——指标不达标属于“可调”范畴；
- ④ 保证回合**不会一开局就注定失败**：既不能已经触发超调/IAE 这类单调门槛（那需要重置才能重来），
  也不能在时限内倒下或越界；
- ⑤ 优先选择“需要真正调参”的初值，但这是**软约束**：见下面的说明。

### 关于“初始参数是否必须赢不了”

最初这里有一条硬规则：初始增益跑满时限不得达标。实测后放弃了硬约束，原因是物理上做不到：

- 对**直流电机、平衡小车、倒立摆**，在 22–60 s 的回合里，几乎任何“结构正确”的 PID 都能达标；
  能让它赢不了的增益要么低于重力阈值（直接倒），要么把 IAE 撑爆（触发单调门槛 = 注定失败）。
- `scripts/calibrate-bands.ts` 在**整段滑块量程**上采样 60 组 × 2 个种子，这三类对象的
  “既不赢也不卡死”区域为 0/60——不是抽样带没调好，而是该区域不存在。

所以现在的行为是：**优先挑需要调参的初值，找不到时退回一个已可达标的初值**（并记录诊断）。
产品上的取舍是“偶尔一轮开局即达标”好于“回合注定失败”或“生成失败”。

实测（`scripts/playability-check.ts`，12 个种子/项目/难度，统计“什么都不做时会发生什么”）：

| 项目 | 初级 | 中级 | 高级 |
| --- | --- | --- | --- |
| 温度 | 需要调参 12/12 | 12/12 | 12/12 |
| 液位 | 12/12 | 12/12 | 12/12 |
| 平衡小车 | 0/12（12 次开局即达标） | 4/12 | 8/12 |
| 倒立摆 | 0/12 | 0/12 | 0/12 |
| 直流电机 | 0/12 | 0/12 | 0/12 |

**已知短板**：直流电机与倒立摆的几乎所有回合，随机初值本身就能达标——这两个对象在
22–38 s 的单回路任务里太容易控制。温度与液位则相反，随机初值几乎总是偏慢。
把电机的回合压到 16 s 可以让初值赢不了，但参考策略也随之达标不了，说明余量已经用尽；
要真正解决需要改任务设计（例如加入饱和工况或更严的调节时间上限），不属于当前范围。

### 实测（`npm run calibrate:gen`，5 个种子/项目/难度）

| 项目 | 初级 | 中级 | 高级 | 单次耗时 |
| --- | --- | --- | --- | --- |
| 温度 | 5/5 | 5/5 | 5/5 | 90–200 ms |
| 直流电机 | 5/5 | 5/5 | 5/5 | 250–430 ms |
| 液位 | 5/5 | 5/5 | 5/5 | 120–900 ms |
| 平衡小车 | 5/5 | 5/5 | 5/5 | 100–170 ms |
| 倒立摆 | 5/5 | 5/5 | 5/5 | 100–200 ms |

单次生成 90–900 ms，在 `loading` 状态下异步执行，不阻塞界面绘制。

## 内部参考策略

`src/challenges/reference-policies.ts` 只在验证逻辑中使用，用于证明“存在可达标的参数组”。

- 它不是标准答案：任何满足公开阈值的增益组合都会被判定成功；
- 它不出现在 UI、日志、成绩导出中（`tests/unit/no-leak.test.ts` 静态扫描 + 运行时断言）；
- 校准方式：`npm run calibrate` 先跑通参考策略，再按需随机搜索。

### 阈值是怎么定的（一次真实的返工）

第一版把 IAE 上限设成参考策略实测值的 1.5–2.5 倍，结果把**合理但偏慢**的响应判死了：
一台直流电机 7.2 s 稳定、稳态误差 0.000、超调 0% 的响应，因为起步爬升的 IAE 399 > 110
被判“本轮已无法达标”。问题在于参考策略 0.9 s 就稳定，它的 IAE 只反映“快”，不代表“合法”。

现在的原则：

- **IAE 是病理响应护栏，不是速度预算**。速度由“调节时间 + 保持时间 + 回合时限”约束，
  时限到了自然判失败，不需要 IAE 提前把回合锁死。
- IAE 上限按“被接受的初始增益”实测分布的 2–3 倍设定（温度 4000/7000/8000、
  电机 800/800/700、液位 55/50/45、角度类 25/30/35），只拦振荡发散。
- **角度类对象不设百分比超调门槛**（`useOvershootGate: false`）。绕零点的角度用
  “峰值偏差 + 稳定时间 + 角速度”约束更合理，这也是规格本身给出的建议；否则扰动后的
  一次摆动就会把回合判死。

## 达标判定


`evaluateVerdict` 的判定顺序（`src/projects/adapter.ts`）：

1. 安全包络 / 数值故障 → **failed**（不可恢复，立即冻结）
2. 超过时限 → **failed**，并指出卡在哪一项
3. 未到最短运行时间 → running（观察期）
4. 超调 / IAE 超限 → running 且标记 `permanent`（本轮已无法达标，可重置）
5. 未进入容差带或保持时间不足 → running
6. 需要扰动但未施加 / 扰动后恢复时间不足 → running
7. 振荡峰峰值过大 / 角速度过大 / 项目专属条件 → running
8. 全部满足 → **success**

超调与 IAE 是单调指标，一旦超限不再“变好”，所以不立即判负而是提示“本轮已无法达标”，
避免用户刚开始就被弹窗打断；时限到达时再以具体原因结束本轮。

**超调统计在“场景扰动”注入时冻结**：阶跃响应的超调只描述扰动前的响应；
扰动后的恢复改由“重新进入容差带并保持 holdTime + IAE”约束。
可选扰动（仅用于探索）不会冻结超调，防止用扰动按钮规避该指标。

## 可复现性与物理参数

- 同一项目的模型参数是模块常量，`nextRound()` 不会改动它们；
- 只有目标、初始状态、初始增益随种子变化；
- 成绩记录保存 `challengeId`、种子派生信息与 `configVersion`，便于复现问题。
